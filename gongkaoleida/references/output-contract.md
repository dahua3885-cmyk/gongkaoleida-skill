# 稳定输出契约

## 一、内部总账

每条公告保留稳定ID，优先使用官方URL或官方公告ID；否则使用“标准化单位＋标题主体＋官方日期”指纹。

内部状态：

- `new_unverified`
- `eligible`
- `watchlist`
- `hard_excluded`
- `stale_closed`
- `verification_blocked`
- `selected`

状态变化保留前值、后值、时间和原因，不直接删除公告。

招录公告内部额外保留：`verification_result`、`score_eligibility`、`terminal_reason`、`单位类别`、`官方待遇原文`、`待遇证据类型`、`内部参考估算及依据`、`基础评分`、`评分版本`、`平台建议`、`运营盲评`和`人工判断依据`。这些字段用于区分“是否完成核验”“是否具备评分资格”和“评分多少”，不与官方事实混写。

`verification_result`只能为`verified`或`evidence_failed`；`score_eligibility`只能为`score_eligible`或`not_scored`。`evidence_failed`会阻断整轮完成；`not_scored`不等于核验失败，也不得保存为数值0。

## 二、用户清单准入

用户只看到同时满足以下条件的公告：

1. 官方原文可靠；
2. 官方日期位于窗口；
3. 报名开始、截止和状态已确认；
4. 报名未截止，或明确尚未开始；
5. 招聘人数已确认；
6. 最低学历已确认；
7. 编制或用工性质已确认；
8. 没有命中硬排除；
9. 评分达到C级以上。

## 三、一个MD内固定双总表

最终只交付一个MD文档。文档内包含两张独立总表，两表分别计数，均按评分从高到低排列，不按S/A/B/C拆成多个区块，用户表不显示等级文字。

### 表一：招录公告表

字段顺序固定为：

```text
归属地市｜公告/单位｜官方发布时间｜报名时间｜当前状态｜人数｜最低学历｜编制/用工性质｜考试内容｜评分｜推荐理由｜官方链接
```

先写：

```text
本轮原始发现 X 条，最终可用 Y 个单位。
```

再给优先制作/优先关注顺序。官方链接直接指向一手页面，不优先给搜索页或聚合转载。

当用户要求“对内评估表”或正在讨论内容制作优先级时，在默认字段基础上增加：

```text
单位类别｜官方待遇｜平台建议
```

`官方待遇`只写公告原文；未披露写“原文未公布”。内部参考估算不得混入该列。`平台建议`不代替数字评分，应说明是抖音优先、小红书优先、双平台或暂不制作。

### 表二：名单型视频素材表

按名单素材评分数字降序排列，字段顺序固定为：

```text
归属地市｜名单阶段｜招录项目｜官方发布时间｜时间池｜样本量/分母｜可分析字段｜已核验发现｜可做选题｜素材评分｜制作难度｜官方名单链接
```

名单阶段固定归一为：`面试资格审查`、`笔试/面试成绩`、`面试入围`、`体检/考察`、`拟录用/拟聘用`、`递补/补录`。一条公告涉及多个阶段时保留组合值。

时间池固定为`近三天新名单`或`历史可复用素材`。表二只展示完成附件解析、分母核验和数据复算的结论，不在用户表复制姓名、身份证号、手机号、完整准考证号/报名号、家庭住址等个人信息。

## 四、考试内容表达

用户表中的“考试内容”采用紧凑格式：

```text
笔试：《职测》《综应》；面试：结构化；总成绩：笔试50%＋面试50%；大纲：官方附件
```

- 至少记录考试方式；原文有信息时继续记录笔试科目、面试形式、体能/技能测试、成绩比例和大纲；
- 考试时间、地点较长时保留在内部总账，用户表只写关键日期或“详见准考证”；
- 原文完全未公布写“原文未公布”；
- 原文写“另行通知”才写“另行通知”；
- 不依据往年公告、相似岗位或培训机构资料推断；
- 考试内容不是用户清单准入硬门槛，不因发布主体尚未公布后续安排而淘汰。

## 五、人数表达

- 公告总人数和目标受众可报人数不一致时写：`本科可报10；公告总计47`；
- 人数只在附件中出现时，注明已从职位表核验；
- “若干”不能擅自换算；
- 标题未写人数但详情已确认时，推荐理由可以说明“标题未写，详情实际X人”。

## 六、日期表达

- 统一使用北京时间；
- 原文只有日期时不补时分；
- 聚合收录时间只在内部保留；
- 距截止24小时内标记即将截止；
- 历史仍可报名不与近三天主榜混排。

## 七、数量勾稽

两类公告分别勾稽，不能混算：

```text
去重后的窗口内招录公告
= 推荐
+ 观察
+ 硬排除
+ 已截止/失效
+ 核验受阻

去重后的名单/进度线索
= 名单型视频素材
+ 普通行政进度
+ 数据不足
+ 重复结论
+ 隐私/合规淘汰
+ 核验受阻
```

用户默认看招录推荐表和名单型视频素材表；普通行政进度等类别只按数量保留在内部。名单素材不计入“最终可用单位数”和招聘总人数。

全量招录审计采用嵌套勾稽，禁止把不同层级的数量并列相加：

```text
发现线索总数
= 正式评分记录数
+ 未评分记录数

正式评分记录数
= 评分大于等于55分
+ 评分低于55分

当前可用数
= 评分大于等于55分
- 复核时已截止/失效数
```

例如本次41条只能表达为`41=14条正式评分+27条未评分`、`14=9条≥55分+5条<55分`、`当前可用8=9条≥55分-1条复核时已截止`。不得把27条未评分写成27条0分。

## 八、全量审计表

用户要求“全部拉出来评分”时，全量表可以同时展示正式评分与未评分记录，但必须遵守：

- 评分列表头写`正式评分`，不写含义模糊的`评分`；
- 通过硬校验的记录写0—100数字；未通过硬校验写`—`，不得写0；
- 另列或在终态原因中明确写窗口外、已截止、非社会招聘、受众硬不匹配、官方未发布必填事实、重复合并等原因；
- `verified + not_scored`表示已经自行核清但不进入评分，不得表述成“核验失败”；
- 全量表按“正式评分降序在前、未评分在后”排序，未评分记录之间按官方日期和发现顺序稳定排序。

## 九、增量变更

每轮固定记录：新增、升级、降级、淘汰、恢复、事实修正、分数变化和来源缺口。没有变化时写“无变化”。

“重新找”不是清空旧名单。公告未再次出现且没有失效证据时，保留上一状态。

## 十、交付前机器验收

交付前必须完成：

1. 每张Markdown表格的表头、分隔行和所有数据行列数一致；
2. 招录公告表实际数据行数等于数量总览的招录公告数；
3. 名单素材表实际数据行数等于数量总览的名单素材数；
4. 最终用户交付只有一个MD，两个底稿可内部保留但不同时作为交付；
5. 用户表不存在S/A/B/C分段标题或等级文字，评分数字保留；
6. 官方链接列存在且不使用搜索结果页替代可用的一手页面；
7. 分开报告`名单候选发现数`、`完成附件分析数`和`剩余未完成数`。仅完成标题路由不得表述为名单附件分析完成。
8. 用户表的评分列不得出现0、空值或`—`；进入用户表的记录必须已通过硬校验且不低于55分。
9. 全量审计表必须用`validate_audit_ledger.ps1`核对正式评分、未评分终态和嵌套数量；任何硬排除0分占位或算术差异都不得交付。
